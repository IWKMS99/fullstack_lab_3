# Лабораторная работа №3. Фильтрация, CRUD и объектное хранилище

RoomFlow — приложение для бронирования переговорных комнат. Основа: [MVP прошлого семестра](https://github.com/IWKMS99/RoomFlow). Backend: Java 24 / Spring Boot 3.5; frontend: React 19 / TypeScript. Использование Java/Spring вместо FastAPI согласовано с преподавателем.

Работа оформлена самостоятельным репозиторием. В истории сохранено развитие исходного MVP; эта версия включает лабораторные №1–3.

## Соответствие заданию

| Требование | Реализация |
|---|---|
| Три параметра и поиск | `/admin`: название (`search`), этаж (`floor`), минимальная вместимость (`minCapacity`) |
| Сортировка и страницы | `name`, `floor`, `capacity`; `asc`/`desc`; API: `page` с 0, `size` от 1 до 100 |
| Сохранение фильтров | Query-параметры TanStack Router; URL можно скопировать и открыть заново |
| Серверная валидация | Bean Validation, разрешённые поля сортировки; неправильные параметры дают 400 |
| CRUD комнат | `AdminRoomController` + `AdminRoomService`; удаление логическое, история бронирований сохраняется |
| Проверка полей и ошибок | Zod/React Hook Form, серверная валидация, 400/401/403/404/409, уведомления |
| S3-совместимое хранилище | MinIO, закрытый bucket; случайные ключи, pre-signed GET URL на 15 минут |
| Загрузка и удаление файлов | `AdminRoomFileService`; метаданные в PostgreSQL; удаление объекта и метаданных |
| Ограничения загрузки | JPEG, PNG, PDF до 5 MiB, проверка MIME и сигнатуры, пустые файлы запрещены |
| Клиент файлов | `RoomFileManager`: выбор, отправка, статус, список, просмотр, удаление, ошибки |
| Проверки | `AdminRoomControllerIT`, `AdminRoomFileControllerIT`, `FileStorageIT` с настоящим MinIO, Vitest |

## Модель доступа

Роли хранятся в `user_roles`, новый зарегистрированный пользователь получает только `ROLE_USER`. Гость — неаутентифицированное состояние, `ROLE_ADMIN` назначается администратором. Сервер проверяет права независимо от доступности кнопок.

| Действие | Гость | Пользователь | Администратор |
|---|---|---|---|
| Смотреть расписание | Да | Да | Да |
| Регистрироваться и входить | Да | Да | Да |
| Создавать бронирование | Нет | Да | Да |
| Смотреть личные бронирования | Нет | Только свои | Только свои |
| Отменять бронирование | Нет | Только своё | Любое |
| Смотреть пользователей, менять роли | Нет | Нет | Да |
| CRUD комнат, фильтры и файлы | Нет | Нет | Да |

Непредъявленный, невалидный или истекший JWT даёт 401; недостаточные права аутентифицированного пользователя — 403. Неизвестная запись — 404, пересекающееся бронирование — 409. Администратор не может снять свою собственную роль. Пользователь не может передать другой `userId` при создании бронирования: владелец определяется из текущей сессии.

## Запуск

Нужны Docker Desktop/Engine с Compose и Python 3 только для генерации локальной конфигурации. Из корня репозитория:

```sh
python scripts/init_env.py
docker compose -f docker-compose.prod.yml up --build -d
```

Откройте http://localhost:8080. Скрипт создаёт `.env` с уникальными локальными паролями и JWT-секретом; файл исключён из Git и не перезаписывается. Данные первого администратора находятся в `BOOTSTRAP_ADMIN_EMAIL` и `BOOTSTRAP_ADMIN_PASSWORD`. Общего предустановленного пароля нет. Bootstrap создаёт аккаунт, только если такой email ещё отсутствует; существующим аккаунтам пароль и роль не меняются. После первого запуска bootstrap-переменные можно очистить. Изменение пароля БД в `.env` не меняет пароль в существующем Docker volume.

```sh
docker compose -f docker-compose.prod.yml logs -f app
docker compose -f docker-compose.prod.yml down
```

Команда `down` сохраняет именованные тома с данными. Разные лабораторные запускайте по очереди: они используют одинаковые локальные порты.

Для разработки backend можно оставить в Compose, а frontend запустить отдельно:

```sh
docker compose up --build -d
cd frontend
npm ci
npm run dev
```

Frontend: http://localhost:5173, API: http://localhost:8081, Swagger: http://localhost:8081/swagger-ui.html. Vite проксирует `/api` на backend. Для запуска Spring без контейнера нужны JDK 24, доступная БД и переменные из `.env` в окружении процесса; Spring сам `.env` не загружает.

## Аутентификация

Access JWT живёт 15 минут, refresh — 7 дней. При обновлении старый refresh отзывается, выпускается новый в том же семействе. Повторное предъявление старого refresh отзывает всё семейство; операция отзыва фиксируется даже при ответе 401. Параллельные обновления сериализуются блокировкой строки. Выход отзывает семейство и очищает cookie. Повторный вход создаёт независимую сессию: выход на одном устройстве не завершает другие. Уже выданный access JWT действует до истечения срока, а изменения ролей учитываются немедленно по данным БД.

Access хранится в localStorage; refresh доступен только через HttpOnly cookie. Для HTTPS необходимо `AUTH_REFRESH_COOKIE_SECURE=true`. Для размещения клиент и API должны иметь общий origin; в локальной разработке это обеспечивает Vite/Nginx proxy.


## Данные и файлы

Пример фильтра: `/admin?search=Room&floor=2&minCapacity=6&page=1&size=10&sort=capacity%2Cdesc`.
API возвращает `content`, `page`, `size`, `totalElements`, `totalPages`, `sort`. Фильтры комбинируются через AND. Смена фильтра сбрасывает страницу.

Файлы привязаны к комнате и управляются администратором. Bucket закрыт; изображение комнаты публичного расписания показывается по временной подписанной ссылке. Обладатель такой ссылки может читать файл до истечения её срока. Если URL истёк, следует обновить список. Удаление комнаты логическое: связанные файлы и старые бронирования сохраняются; отдельная кнопка удаления файла удаляет и S3-объект, и запись. При ошибке сохранения метаданных после загрузки выполняется компенсирующее удаление объекта. Между PostgreSQL и S3 нет распределённой транзакции.

`FileStorageIT` поднимает настоящий MinIO, загружает PDF, читает его по подписанной ссылке, проверяет запрет анонимного чтения, удаляет объект и проверяет 404, отказ MIME-подмены и превышения размера.

## Проверка

Docker должен быть запущен: серверные интеграционные тесты поднимают отдельные контейнеры PostgreSQL и MinIO, не используют рабочую БД. JDK 24 и Node.js 22+ нужны для проверок вне контейнера.

```sh
./gradlew check
cd frontend
npm ci
npm run lint
npm run test
npm run build
```

В PowerShell вместо `./gradlew` используйте `.\gradlew.bat`. `check` включает JUnit/MockMvc, Spotless, PMD и SpotBugs. GitHub Actions запускает серверные проверки и frontend lint/build/Vitest при push и pull request в `main`. Проверки не требуют секретов GitHub.

Дополнительно `npx playwright install chromium && npm run test:e2e` проверяет 10 сценариев интерфейса с подменой API: календарь, формы, маршруты и ролевые экраны. Для установленного Google Chrome можно задать `PW_CHANNEL=chrome`. Workflow `Frontend E2E` запускается вручную через Actions. Реальные серверные операции и S3 проверяются отдельно JUnit/MockMvc и `FileStorageIT`.
